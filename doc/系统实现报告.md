### 5.3 遇到的问题及解决方案

#### 案例 1：Spring MVC 参数绑定失败

**【问题描述】**：新增的 Controller 方法使用 `@PathVariable Long id` 注解，运行时抛出 `IllegalArgumentException: Name for argument of type [java.lang.Long] not specified`。原有 Controller 却正常工作。

**【AI 的建议】**：AI 建议在 `@PathVariable` 中显式指定 value 属性 `@PathVariable("id")`，原因是 Java 编译默认不保留方法参数名，Spring 无法自动映射。

**【实际采纳情况】**：■ 完全采纳

**【最终解决方案】**：批量替换所有 `@PathVariable Long xxx` 为 `@PathVariable("xxx") Long xxx`，涉及 10 个 Controller 方法。

**【反思】**：这个问题说明显式优于隐式——Spring 官方推荐的做法就是显式指定 value，不应该依赖编译器行为。AI 定位问题准确、方案直接有效。

#### 案例 2：Holt-Winters 乘法模型预测值异常放大

**【问题描述】**：日销售额均值约 ¥5000，但预测 API 返回 ¥80,000+。排查发现乘法季节性因子在某些稀疏日期接近 0，除法运算（Yt/St）将水平值放大数千倍。

**【AI 的建议】**：AI 建议改用加法季节性模型替代乘法模型，并引入变异系数 CV 作为自适应切换条件——当 CV > 3.0 时自动降级为线性回归。

**【实际采纳情况】**：■ 完全采纳

**【最终解决方案】**：重写 `salesForecast()` 方法为加法 Holt-Winters，添加 `linearRegressionForecast()` 兜底方案。修复后预测值恢复合理范围（日均 ¥20,000 → 预测 ¥17,000-22,000）。

**【反思】**：AI 提供了两种方案（加法模型 + 线性回归兜底），最终联合采用。这让我意识到算法不能只看公式，还要考虑数据质量——真实世界的推荐/预测系统都有多级降级策略。

#### 案例 3：WSL 下 Docker bind mount 图片无法加载

**【问题描述】**：Docker Desktop for Windows 无法将 WSL 文件系统路径 `./uploads` 做 bind mount 到容器，商品图片全部 404。但同样的 `docker-compose.yml` 在其他环境中正常。

**【AI 的建议】**：AI 建议改用 Docker 命名卷 `uploads_data`，通过 `docker cp` 将宿主机图片导入卷中；同时在纯 Linux 服务器部署时切换回 bind mount 以获得更好的可维护性。

**【实际采纳情况】**：■ 完全采纳

**【最终解决方案】**：修改 `docker-compose.yml` 为命名卷方案，编写自动化脚本验证。服务器部署时改回 bind mount。

**【反思】**：跨平台兼容性是 Docker 宣传的优势，但实际使用中 WSL2 + Docker Desktop 仍有不少坑。AI 快速定位了 WSL 与原生 Linux 在文件系统映射上的差异，并给出了双策略方案（开发用卷，生产用 mount），兼顾了便利性和可维护性。

### 5.4 对 AI 辅助编程的思考（500 字以上）

**AI 生成的代码，你是否都能理解？如不能，如何处理？**

大部分 CRUD 代码（Controller/Service/Mapper）结构清晰，可以直接理解。但对于 Holt-Winters 季节性预测、Jaccard 协同过滤这类算法代码，我会先让 AI 解释原理，再对照数学公式逐行确认逻辑。如果某段代码不能理解，我会要求 AI 加上详细注释或用更简单的方式重写，不会盲目接受。比如预测算法从乘法模型到加法模型的转变，就是在理解了数学原理后做出的主动决策。

**有没有 AI 给出错误建议的经历？如何识别和避免？**

有过。AI 最初建议使用乘法季节性 Holt-Winters，这在理论上正确，但对稀疏数据会严重放大误差。识别的方法是将 AI 生成的代码放到真实数据中跑一遍——预测值从 ¥5000 跳到 ¥80000，明显不合理。避免的方法：对 AI 的输出保持批判态度，关键算法必须用实际数据验证，不依赖 AI 自己说"这样是对的"。

**你认为 AI 会取代初级程序员吗？为什么？**

短期内不会完全取代，但会显著改变初级程序员的工作内容。AI 已经能完成 80% 的样板代码编写（CRUD、SQL、配置），初级程序员不再需要手写这些。但 AI 目前无法替代的能力包括：理解复杂业务需求、做出架构决策、判断代码的边界条件和安全性、调试跨系统问题。未来初级程序员的角色会从"码农"转变为"AI 协作者"——核心能力是 prompt engineering、代码审查、方案验证，而不是从零手写。

**经过这次项目，你对"程序员的核心竞争力"有什么新的理解？**

核心竞争力不再是"能写多少代码"，而是三个层次：第一，**判断力**——能否识别 AI 输出的正确性和边界情况；第二，**系统思维**——能否将复杂需求拆解为可实现的模块、设计合理的架构；第三，**沟通能力**——能否将需求准确描述给 AI、给团队成员、给 stakeholders。这个项目中，所有代码 AI 都可以帮你写，但"要做哪些模块""用什么技术方案""怎么验证对不对"这些决策只能你自己做。

**如果下次再做类似项目，你会如何更好地利用 AI？**

1. 先花更多时间在需求分析和架构设计上（人和 AI 协作的起点越高，后续效率越高）
2. 建立项目级的 CLAUDE.md 和 coding conventions，让 AI 更懂项目上下文
3. 关键算法先让 AI 写单元测试，再用测试驱动开发验证正确性
4. 报告写作与开发同步进行，每完成一个模块立刻让 AI 生成对应章节，最后人工润色整合
